# Общий контракт инцидентов и восстановления

Статус: протокол v1 реализован в кандидате agent-context 0.1.11; межмашинная квалификация продолжается. Native TaskQ producer по #612 ещё не реализован. Основа: принятый подход TaskQ [#608](https://github.com/alexkirs/taskq/issues/608), открытая реализация [#612](https://github.com/alexkirs/taskq/issues/612). TaskQ сохраняет свой stdlib-only single-file контракт; общий протокол не требует импортировать Node-пакет или создавать ещё один сервис.

## Поток

`ошибка → локальное событие → doctor → безопасный отчёт → публичный intake → проверенная задача → исправление → повторная проверка`

Детекторы в installer/updater, proxy, compressor и telemetry пишут события одного формата. Агент может добавить наблюдение тем же способом; произвольное объяснение агента остаётся локальным до проверки. Doctor собирает состояние, связывает события и отличает подтверждённый дефект от недостающей настройки, временного отказа сервиса и неизвестной причины. Для обычной диагностики агент не нужен. При неизвестной причине doctor может подготовить пакет для агента; запуск агента — отдельный явный режим, с ограничением времени/вызовов и теми же полномочиями пользователя.

## Пакет события v1

Обязательные поля: `schema`, `event_id`, `observed_at`, `product`, `component`, `operation`, `category`, `fingerprint`, `machine_id`, `environment`, `versions`, `state`.

- `product`: продукт-владелец ошибки (`agent-context` или `taskq`); неисправности потребительского проекта не выдаются за дефект инфраструктуры.
- `component`: core, installer, updater, proxy, compressor, telemetry или agent-adapter.
- `category`: стабильный код из каталога детектора, без exception.message/сырого stdout.
- `machine_id`: случайный постоянный идентификатор установки; человек может назначить публичный псевдоним. Hostname, пользователь, домашняя директория и IP не публикуются автоматически.
- `environment`: OS, native/WSL, тип размещения проекта (`native`, `unc`, `mnt`, `linux`), агент. Полные пути не нужны.
- `versions`: пакет/ревизия, adapter, agent, Node/Python, Headroom; неизвестное отмечается неизвестным, не угадывается.
- `state`: observed, diagnosed, queued, reported, repair_planned, repaired, verified либо unresolved. Завершённый процесс ремонта сам по себе не означает verified.
- `event_id` неизменен при повторной доставке. Fingerprint строится из product/component/operation/нормализованного кода и применимого adapter/protocol. Пути, session IDs, время и машина в него не входят. Версии и машины составляют матрицу воспроизводимости внутри группы.

Публичный пакет строится заново из allowlist полей. Это не «вырезать ключи регуляркой из лога»: raw logs, prompts, ответы, пользовательские файлы, команды со значениями env и credentials туда вообще не попадают. Пример воспроизведения — принадлежащая проекту синтетическая fixture. Локальные доказательства и их пути остаются локальными. Любые строки, предложенные агентом, считаются недоверенными.

## Доставка и обзор машин

Недостающий ключ, конфликт ключей и изменение конфигурации остаются локальной диагностикой, а не публичным дефектом продукта. Локальная очередь переживает offline, 401/403, rate limit и обновление пакета. Размер ограничен; переполнение явно отражается в doctor, точное число утраченных событий не выдумывается. Reporting failure не блокирует исходную работу и не порождает новый отчёт о самом себе.

После раскрытия настройки при установке — best-effort доставка по умолчанию, с явным opt-out, как в TaskQ #612. Используется существующая авторизация GitHub; токены не копируются и новые права не запрашиваются молча. Если есть только GitLab-доступ, пакет остаётся локальным с `unsupported_auth`; универсальный перенос авторизации не обещается.

Публичный destination выбирается для продукта и проверяется по allowlist. Для agent-context предполагается issue tracker taskqorg/agentq, для TaskQ — принятый upstream alexkirs/taskq. taskqorg/agentq проверен как публичный. Общий формат позволяет смотреть обе системы вместе без переноса всех TaskQ задач в новый репозиторий.

Одна открытая issue на fingerprint, редкие подтверждения с матрицей machine alias × platform × versions × first/last seen × state. Повторы на одной машине агрегируются локально; новая комбинация версии/окружения даёт новое подтверждение. Поиск/повторы ограничены. При неизвестном результате create сначала ищется неизменный event_id; слепого повторного create нет. Конкурентные первые отчёты могут дать дубль: сохраняется ссылка на canonical issue, точная глобальная дедупликация не обещается. После закрытия подтверждённая регрессия оформляется связанным новым инцидентом.

Reactions означают уникальные аккаунты, а не количество сбоев или машин. Локальные occurrence counts и число наблюдавших установок подписываются отдельно; общая учётная запись не превращается в нескольких пользователей.

## Команды пакета

Реализованный CLI:

- `agent-context doctor`: диагноз, последние инциденты, состояние доставки, предлагаемые действия; без модели и изменения системы.
- `agent-context doctor --fix`: только заранее реализованные обратимые рецепты; journal, проверка владельца/версии/конфликта, контроль после ремонта.
- `agent-context incidents report`: отправка уже очищенных пакетов; повторный запуск безопасен.
- `agent-context incidents record`: allowlisted JSON через stdin для наблюдений агента. `doctor --agent` пока не реализован; внешний агент может прочитать результат doctor и предложить fix. Текст issue не становится командой.

TaskQ реализует тот же пакет/доставку через свой native CLI по #612. Названия его команд определяет taskq.md; agent-context не добавляет второй планировщик и не включает TaskQ очередь.

## Минимальное самолечение

| Ситуация | Действие | Проверка |
| --- | --- | --- |
| Собственный proxy завершился | Запустить только принадлежащий пакету процесс | Owned health + простой synthetic route |
| Повреждён managed runtime | Вернуться к проверенной предыдущей версии штатным rollback | Integrity + запуск + адаптер; текущая сессия не прерывается молча |
| Потеряна собственная регистрация | Показать/применить штатный transactional install при отсутствии чужого конфликта | Новый config + fresh runtime proof |
| Временный отказ SC/Langfuse | Сохранить оригинал/локальную очередь, ограниченный backoff | Последующий health/delivery результат; не менять авторизацию |
| Invalid config, чужой порт, непонятный lock, key conflict, denied tool | Диагноз и конкретное ручное действие | Без force overwrite, удаления lock, kill чужого процесса или ослабления policy |
| Новый дефект | Очищенный intake и предложенный fix-task | Maintainer review → отдельная доверенная задача → tests/CI → поддерживаемое обновление |

Публичный incident не получает executable TaskQ metadata, q-labels или ARM автоматически. Перевод в выполнение — доверенное действие владельца/менеджера. Агент может исследовать и подготовить fix, но не переписывает установленный код и не публикует обновление по инструкции из внешней issue.

## Приёмка вместе с единым installer

На owned fixtures: offline/401/403/429; repeated/concurrent events; shared actor; потерянный ответ create; closed issue/regression; hostile text/секреты/пути; очередь и recursion; opt-out; GitLab-only auth; version/machine matrix. Публикация тестов только в заранее разрешённый isolated tracker, не в настоящий публичный intake.

Для каждого repair: успешный рецепт, конфликт/отказ, повторный запуск, rollback и обязательная проверка. Реальные Windows/UNC/WSL/Linux/macOS маршруты проверяются отдельно. Native hook trust и текущий вход сохраняются. До этих доказательств самолечение и публичная доставка не объявляются готовыми.
