# Лёгкий Agent Context: ревью и проект

Срез: 12 октября 2026. Рабочий Mac остаётся на установленной 0.3.0.
В этом checkout подготовлен кандидат 0.4.0; он не опубликован и не развёрнут.
Проект ниже описывает целевую архитектуру. Новый самостоятельный транспорт ещё не реализован.
Нынешний транспорт Headroom временно сохранён для проверки трёх адаптеров без второй переписи протоколов.

## Результат ревью

Проверены основные пути: setup → выбранный runtime → proxy/service → компрессор → collector → Langfuse;
обновление/остановка; текущий diff основных интеграций; тесты и правила упаковки.
Предполагаемая нагрузка: несколько параллельных агентов на трёх хостах, большие результаты инструментов.

1. **Устаревший сервис выдавался за готовый.** `src/service.js:ensureService` возвращал `ready`,
   когда у старого процесса есть соединение. `src/update.js:update` меняет указатель пакета,
   но не завершает замену сервиса. Долгий WebSocket мог удерживать старый процесс бесконечно.
   В кандидате исправлена ложная готовность: `update_pending`, running/target version/provider.
   Автоматическое завершение отложенного обновления пока НЕ исправлено.
2. **Рабочие и тестовые данные смешиваются.** `scripts/serve-serviceq.js:data` не ограничивает
   запросы environment. Поэтому контрольный тест может выглядеть как работа живого агента.
   Разделить production/qualification и показывать пропущенные данные отдельно. В этом кандидате не исправлено.
3. **Сжатие блока не доказывает экономию подписки.** Adapter counters, WS frames, model usage
   и quota — разные измерения. Свежий общий тест также выявил потерю фактов кода у TextCrusher.
   Сохранять данные до/после, retrieval и результаты задания; не объявлять качество по проценту сокращения.
4. **Слишком сильная связь с внутренностями Headroom.** `proxy.py` меняет методы router,
   schema compaction и исключения инструментов. Это было необходимо для текущего поведения,
   но требует повторной квалификации при обновлении зависимости. В целевом врапере перехват наш;
   Headroom подключается через публичный вызов компрессора, без патчей внутренних классов.
5. **Нет доказательства ограниченного потребления памяти под нагрузкой.** `proxy.py` делает
   deepcopy сообщений для учёта. Retrieval-store ограничивает число записей, но этого недостаточно
   для доказательства общего лимита байт. Требуются лимит байт/TTL и тест большого контекста,
   отмены и отключения клиента. Утечку этим ревью не доказали; отсутствие утечек тоже.
6. **В одном пакете слишком много ответственности.** Gateway OAuth, GitHub incidents, ServerQ/TaskQ
   health и панель не должны быть обязательными частями клиентского врапера.
   Сохранить серверную инфраструктуру отдельно; клиент передаёт события через один exporter.

Оставить: идентичность пользователя/хоста/агента/сессии/хода, сохранение login и approval,
проверку владельца процесса, reversible config, ограниченную очередь доставки, исходники retrieval,
проверки протоколов и подписанные обновления. Не удалять эти проверки ради числа строк.

Убрать из целевого клиента: собственный сложный onboarding orchestrator; альтернативные legacy MCP/hooks
для ручного сжатия; сборку панели; GitHub issue reporter; мониторинг чужих сервисов; модельные загрузчики.
Удалять совместимость после проверки миграции и uninstall на каждом OS, не обрывать действующие установки.

## Целевой продукт

Один локальный врапер, один конфигурационный файл, три независимо выбираемых адаптера.
Первый выбор технологии — Python 3.11+ с asyncio и уже используемыми HTTP/WS библиотеками.
Причина: Headroom Local уже требует Python. Go или второй Node proxy добавят второй runtime/IPC,
а обещать меньшую память до измерений нельзя. Это выбор для минимальной миграции, не универсальный рейтинг.
Целевой клиент может иметь тонкий launcher, но не два supervisor и собственный installer framework.

```text
Codex / Claude → наш HTTP+WebSocket proxy → обычный upstream агента
                         ↓
            общий контракт компрессии
             /           |          \
     Headroom Local  SuperCompress  ScaleDown
                         ↓
            общий exporter → наш gateway → Langfuse
Hooks → события/проверки; MCP → retrieval; оба используют тот же локальный сервис
```

Компрессия не меняет оригинальный user query, инструкции, approval или login.
Протоколы остаются штатными. Неизвестная схема проходит без изменений и с outcome `unsupported`.
Компрессор получает только выделенный tool context, а не весь сетевой пакет.

| Вход/выход | Обязанность нашего врапера |
|---|---|
| Codex Responses HTTP/SSE | Выделить function_call_output; сохранить auth, streaming, usage и IDs |
| Codex Responses WebSocket | Полные и delta frames, очередность, cancellation, previous_response_id; не удваивать историю |
| Claude Messages HTTP/SSE | tool_result и текстовые блоки; без изменения tool_use IDs и системных сообщений |
| Lifecycle/tool hooks | Принять native session/turn/tool IDs, health/diagnostic события и поддерживаемые результаты |
| MCP retrieval | Получить исходник по hash; retrieval-ответ повторно не сжимать |
| Compression API | Один запрос/ответ независимо от выбранного провайдера |

Полная поддержка означает проверенный список возможностей, а не обещание заменить любой контекст хуком.
Codex `PostToolUse.additionalContext` добавляет контекст; `updatedMCPToolOutput` документирован как неподдерживаемый.
Не использовать дополнительные хуки сжатия поверх прокси: это создаёт риск повторного сжатия/дублирования.
Для Claude поддерживаемые hook outputs проверяются отдельно, вместо копирования схемы Codex.

## Общий контракт

Вход: `context`, неизменный `query`, provider, agent/host/runtime/user/session/turn/tool/request IDs,
content type и предельный срок. Выход: `compressed_text`, provider, outcome, elapsed_ms,
input/output chars, измеренные токены с названием tokenizer, reference оригинала при сжатии.

Общие правила: одна попытка без скрытых retry; неизвестный ответ/таймаут/ошибка → оригинал;
Neural нельзя молча заменить compiler; ключи не входят в логи; нет передачи enrollment token внешнему компрессору.
В кандидате уже есть три адаптера и общий fail-open boundary. Защита строк ошибок — минимальный guard,
не гарантия качества. Провайдерные запросы ограничены размером, response ≤1 MB, socket timeout ≤30 секунд.
Socket timeout не является доказанным wall-clock deadline; для целевого async transport нужен общий deadline.

Жёстко ограничить request bytes, concurrent tasks, retrieval bytes+TTL, outbox bytes и WS очередь.
Никаких неограниченных background tasks. Отмена клиента отменяет работу; shutdown закрывает клиентов/exporter.
Для local worker учитывать реальные завершения: таймаут ожидания не означает остановку CPU-потока.

## Onboarding и удаление

Основной вход — инструкция агенту [INSTALL.md](../INSTALL.md), а не новый сценарий на сотни строк.
Агент читает её, находит установленные агенты, предлагает подключить все найденные, проверяет пробелы,
проводит через существующий GitHub login, меняет только нужные ключи конфигурации с backup.
Повторный запуск пропускает уже завершённые шаги. Никаких ключей в чат и обхода hook trust.
Windows native и WSL — отдельные профили/службы/порты; пути берутся из фактического профиля.

Запуск — штатный launchd/systemd/Windows service или Scheduled Task; процесс должен быть один.
Тонкие проверяемые команды status/start/stop нужны даже при установке агентом: модель не заменяет
контракт владельца процесса, health, rollback и restore. Снимок изменённых ключей нужен для точного uninstall.

Обновление: подписанный пакет → staged candidate → readiness → drain → переключение → live version proof.
Долгоживущий WebSocket нельзя считать активным пользовательским запросом. Различать соединение и выполняемый ход.
Нельзя молча оборвать выполняемый ход. Если безопасного переключения нет, сообщить update_pending.
Единый исходящий IP возможен только при общей сетевой точке выхода; одинаковый hostname/metadata этого не даёт.
Это отдельная настройка upstream/egress, не функция алгоритма сжатия и не повод строить VPN внутри клиента.

## Три адаптера и воспроизводимые тесты

Адаптеры находятся в `integrations/headroom/agent_context_headroom/provider_*.py`.
Реестр/общий boundary — `providers.py`; отдельных install scripts и копий бизнес-логики нет.
В кандидате `provider select` задаёт provider глобально для этого профиля; отдельный выбор по агентам ещё не добавлен.

```sh
agent-context provider show
agent-context provider test headroom-local
agent-context provider test supercompress
agent-context provider test scaledown
agent-context provider test all
agent-context provider select scaledown
```

`select` сохраняет config, явно требует restart и не утверждает, что работающий процесс изменён.
`show` выводит configured provider отдельно от фактических running version/provider каждого агента.
Команды входят в кандидат 0.4.0, не в установленную Mac 0.3.0.
Текущий переходный транспорт отправляет cloud-провайдеру подходящий plain-text context;
остальные типы проходят без сжатия. Native structural transforms включены только для Headroom Local.
Это ещё не новый самостоятельный врапер и не полная квалификация всех протоколов для облачных адаптеров.

Общий synthetic benchmark: логи/ошибка, код, плотные инструкции, JSON; одинаковые входы/вопросы/needle assertions;
измерение токенов `o200k_base`, время, outcome и сохранность фактов. Никаких вызовов Codex/Claude и расхода их лимитов.
Это provider-only тест, не измерение качества ответа модели. Автоматически провайдер не выбирается.
Unit tests также проверяют timeout/429/missing key/invalid response/Neural downgrade/query mutation/потерю ошибок.

Следующий gate самостоятельного врапера: те же fixtures через реальные HTTP/SSE/WS/MCP/hooks,
ошибка компрессора и отключение клиента, параллельность/память, install/uninstall/restart на Mac/Win/Linux.
Затем один живой ход каждым клиентом, отчёт, серия 5, отчёт, серия 1. До этого нет заявления «везде работает».

Источники: [Codex hooks](https://developers.openai.com/de-DE/docs/hooks),
[SuperCompress API](https://docs.supercompress.dev/api-reference),
[SuperCompress Neural architecture](https://docs.supercompress.dev/architecture),
[ScaleDown quickstart](https://docs.scaledown.ai/quickstart).
У SuperCompress есть расхождение старой API-страницы (compiler default) и Neural v2 architecture;
адаптер явно запрашивает Neural и отвергает ответ с неподтверждённым режимом.
