# Онбординг и удаление через агента

## Короткий сценарий в чате

Агент сопровождает пользователя целиком. Пользователь не должен вручную выполнять цепочку команд или искать сервисные ключи.

1. Запустите `agent-context onboard`. Это предварительная проверка без записи настроек и без входа: готовые профили Codex, Claude Code и Hermes, текущая ОС/WSL, Python с venv/ensurepip, наличие сохранённого подключения команды. Агент без профиля требует обычного первого запуска/входа. Не выдавайте обнаружение за успешную установку. Дополнительные агенты Headroom пока не входят в этот установщик.
2. Скажите кратко: «Нашёл Codex и Claude Code. Подключу локальное сжатие, телеметрию, мониторинг и автообновления. Подключить обоих?» Все найденные готовые профили — рекомендуемый выбор; пользователь может исключить лишние. Если пользователь уже явно попросил подключить этих агентов, не спрашивайте повторно. Для TaskQ используйте известный список его рабочих агентов из конфигурации проекта; не заставляйте пользователя перечислять его заново и не меняйте модели/входы/approval TaskQ.
3. Устраните только перечисленные препятствия. Нестандартные пути профилей пока требуют отдельной проверки: не подменяйте их стандартным домашним каталогом. При необходимости установки системных зависимостей объясните конкретное действие. Существующие ключи и входы повторно не запрашивайте.
4. После согласия выполните `agent-context onboard --yes` либо `agent-context onboard codex claude --yes`. Телеметрия входит в стандартный пакет. Без сохранённого доступа начинается один GitHub Device Flow к gateway команды, затем настройка продолжается автоматически; сервисные ключи сотрудникам не нужны. Другой gateway задаётся через `--gateway <HTTPS URL>`. Существующий вход используется повторно; `--login` нужен только для восстановления отозванного доступа. `--no-report` отключает отправку инцидентов, `--migrate` разрешает рассмотренную миграцию версий.
5. Онбординг выполняет `setup`, проверку/восстановление служб, проверку доставки отдельно для каждого выбранного агента, отправку снимка мониторинга и итоговую диагностику. Явное отключение телеметрии владельцем не перезаписывается: онбординг показывает препятствие. `ready_for_agent_check` означает готовность к реальному контрольному ходу, а не доказанное сжатие. Агент сопровождения завершает обычные login/hook-trust шаги и проверяет реальный ход каждого выбранного агента без прерывания активных сессий. Пока есть блокеры, показывайте их, а не «всё готово».
6. Итог для пользователя: кто подключён, что реально проверено, работают ли автообновления и какое действие осталось. Не показывайте техническую JSON-простыню. Повторный запуск продолжает существующую установку и использует сохранённый вход.

Кандидат 0.4.4: один MCP `agent_context` с `index_document`, `search_document`, `get_original`; CLI `tools run` для native команд. RTK и context-mode — внутренние закреплённые пакеты. Общая компрессия Headroom отключена; прежний прокси сохранён для маршрутизации и телеметрии. Новые MCP/hooks требуют обычного trust; setup не меняет login/model/approval. Ни ключ облачного сжатия, ни загрузка моделей не нужны. Кандидат ещё не означает развёртывание на рабочих машинах.


## Подключение команды без сервисных ключей

Стандартный онбординг включает командную телеметрию. Само сжатие выполняется локально, в том числе при недоступности мониторинга. GitHub Device Flow даёт устройству доступ к общей телеметрии и уведомлениям обновлений. Процедура владельца: [TEAM-ONBOARDING.md](docs/TEAM-ONBOARDING.md); содержащиеся там результаты прежних версий не являются квалификацией 0.3.0.

Если команда предоставила адрес готового gateway, агент объясняет передачу native conversation/tool telemetry в Langfuse; сжатие выполняется локально. Затем запускает `agent-context connect <HTTPS gateway URL>` в локальном терминале и показывает пользователю только ссылку `https://github.com/login/device` и временный публичный код. Пользователь подтверждает доступ на GitHub. OAuth token, device token и сервисные ключи в чат не передаются. После успешного подключения агент выполняет `setup`, `doctor --fix --live`, `telemetry verify` и настоящий ход для каждого установленного агента; обычные login/model/approval и native hook trust сохраняются.

В этом режиме отдельные Langfuse credentials у сотрудника не запрашиваются. Профиль хранит только отзываемый доступ устройства; native exporters отправляют OTLP в loopback proxy с закрытой ограниченной очередью. Native Windows и WSL получают разные устройства и порты. Если native exporter отсутствует или hook не доверен, это остаётся `needs_attention`, а не успешной настройкой. Явное отключение capture владельцем сохраняется. Обычный прямой режим ниже остаётся доступен для независимой установки.

Текущий кандидат усиленной телеметрии: [TELEMETRY-DELIVERY.md](docs/TELEMETRY-DELIVERY.md). `setup` теперь требует валидных credentials, native exporter и проверенной доставки для статуса `configured`; при их отсутствии сжатие сохраняется, onboarding сообщает `needs_attention`. Проверка доставки: `agent-context telemetry verify`, только небольшой синтетический OTLP span. Проверка реального native exporter выполняется отдельно.

Для отдельного подключения Langfuse без команды агент объясняет, какие данные отправляются, и предлагает `agent-context set-langfuse` в локальном терминале. Ввод скрыт; ключи не запрашиваются в чате и не передаются в argv/log. Сжатие от этой настройки не зависит. Старый `set-key` оставлен для совместимости, локальный компрессор его ключ не использует. Native hook trust не обходится; официальный exporter остаётся собственностью агента и сохраняется при удалении пакета.

Этот файл — процедура для Codex, Claude Code и Hermes, когда пользователь просит установить или удалить Agent Context. Канонический репозиторий: https://github.com/taskqorg/agent-context. Не выдавайте установку кандидата за квалифицированный стабильный релиз.

## Установка

1. Определите OS пользователя агента и его фактический профиль. Native Windows и WSL — разные установки; Windows-проект в WSL не превращает Windows-агента в Linux-агента. Дополнительные профили требуют отдельной проверки. Не переносите входы между хостами.
2. Проверьте Node 22.5+, npm, Git и установленный Python 3.11–3.13 с поддержкой `venv`/`ensurepip`. На Debian/Ubuntu/WSL может потребоваться отдельный пакет `python3.12-venv` (подставьте версию Python). Если зависимости отсутствуют, назовите недостающие и согласуйте установку системных зависимостей. Не заменяйте системный Python. Уже установленный подходящий интерпретатор можно выбрать через `AGENT_CONTEXT_PYTHON`. Объясните: прокси только маршрутизирует; шумные поддерживаемые команды выполняются через наш CLI, большие справочные документы — через наш MCP. Сторонние хуки и install-скрипты движков не устанавливаются. Langfuse необязателен. Публичные инциденты — только разрешённые метаданные; предложите `--no-report`, если пользователь не хочет отправку.
3. Прочитайте существующие настройки только установленных агентов и текущего проекта. Не выводите ключи, login-файлы или полный config. Найденное другое сжатие покажите пользователю. При разрешении удалить его сохраните закрытые копии и удалите только подтверждённые конфликтующие подключения. Не отключайте другие плагины по догадке. Не заменяйте неизвестный custom provider/proxy.
4. Не запрашивайте ключ сжатия. Сохранённая телеметрия используется автоматически, её отсутствие не блокирует установку. Для новой команды используйте `onboard --gateway <HTTPS URL> --yes`; приватные сервисные ключи сотрудникам не нужны.
5. В подготовленной среде:

   ```sh
   npm exec --yes --ignore-scripts --package=github:taskqorg/agent-context -- agent-context setup
   ```

   Для рассмотренной версии закрепите полный Git SHA вместо moving main. Альтернатива для разработки/удаления прежнего пакета: отдельный checkout этого репозитория, `npm ci --ignore-scripts`, `node bin/agent-context.js setup`. Не клонируйте поверх существующего проекта. Пакет не устанавливает самих агентов и не открывает новую подписку.
6. Прочитайте `onboarding`, отсутствующие агенты, предупреждения и ошибки. `needs_attention` требует исправления перечисленных условий. Пропущенный агент не считается настроенным. Выполните `doctor --fix --live` через установленный CLI или приватный launcher (`node <home>/.agent-context/launcher.mjs doctor --fix --live`). Эта установка через npm exec не создаёт постоянную глобальную shell-команду.
7. Перезагрузите подключения штатным способом, не прерывая чужие активные сессии. Выполните один разрешённый синтетический tool-result тест у каждого проверяемого агента. Не меняйте approval policy, вход или модель ради теста. При отсутствии разрешённого инструмента назовите блокер; не обходите его.
8. Дайте короткий результат: установленные агенты и версия, сервисы, конфликты, локальный компрессор, доставка телеметрии по каждому агенту, автообновления, действительная runtime-проверка и оставшиеся блокеры. Health, размер текста и реальные model-input token savings — разные доказательства. С 0.2.6 `setup` устанавливает постоянный monitor: он подписан на проверенные stable-релизы через gateway и проверяет обновления раз в час даже без запуска агента. Новый релиз запускает раннюю проверку; новые minor/major требуют миграции. На Linux проверьте user systemd и lingering; не включайте системные настройки без разрешения. Если регистрация monitor вернула `needs_attention`, автообновления в фоне не подтверждены. Для прежних пилотов: рассмотренный пакет `update bootstrap --migrate`, затем `monitor install --migrate`; это не меняет настройки и вход агентов.

## Историческая телеметрия 0.3.0

- Native exporter: разговоры, инструменты и доступные ему фактические токены/стоимость. Codex и Claude устанавливаются через официальный plugin workflow; trust не обходится. Если у Hermes отсутствует штатный Langfuse exporter, онбординг требует завершить его native подключение и не объявляет готовность.
- Локальное сжатие: события для структурных обработчиков и обычного текста, стратегия, результат, длительность, объём до/после, agent/host/runtime и доступные native session/turn IDs. При ошибке сохраняется оригинал. Содержимое не копируется в метаданные событий сжатия.
- Монитор: здоровье служб, очередь и задержка доставки, сбои, версии, суммарная/максимальная длительность сжатия и время последней попытки. Проверка доставки отдельно для каждого агента повторяется ежедневно, после неудачи — не чаще раза в час, вне пути запроса модели.
- Снижение числа символов не считается экономией оплаченных токенов. Синтетическая проверка доставки не доказывает работу native hooks или полный охват запросов модели. Явные пропуски остаются видимыми.

Перед установкой клиентов 0.3.0 обновите gateway до того же кандидата: прежняя строгая схема отвергает новые поля мониторинга. Квалификация в изоляции не является выпуском или развёртыванием на рабочих Mac/Windows/FRA.

## Полное удаление

Просьба пользователя удалить пакет разрешает этот шаг. Не удаляйте действующие профили на машинах только ради проверки процедуры.

1. Попросите завершить остальные сессии, использующие proxy; удаляйте из отдельного терминала/агента, который не использует удаляемый proxy. Занятый сервис возвращает отказ, без убийства процесса. На каждом OS-профиле процедура отдельная.
2. Если установленная версия ещё не поддерживает uninstall, подготовьте отдельный свежий checkout репозитория и зависимости; запускайте `node bin/agent-context.js uninstall`. Новая установка для этого не нужна. После появления команды в установленной версии можно использовать CLI или приватный launcher.
3. Сначала `uninstall --dry-run`: проверьте перечисленные пути восстановления, migrated plugins и каталог данных. Preview не изменяет файлы и не останавливает сервисы.
4. Выполните `uninstall`. Команда проверяет журналы и backup hashes, восстанавливает изменения всех завершённых установок, останавливает только свои сервисы после проверки owner/PID и control token, удаляет свои данные и global npm-пакет. Установка/обновление сериализованы с удалением. Не удаляйте `.agent-context` вручную до восстановления настроек.
5. Более поздние изменения других JSON/TOML/YAML настроек сохраняются. При таком слиянии TOML/YAML форматируется заново; full-line comments сохраняются, inline comments могут потеряться. Изменённые собственные значения, неизвестные/повреждённые журналы, symlinks или живой сервис с неподтверждённой идентичностью вызывают отказ. Сохраните локальную квитанцию и согласуйте точечное исправление — не обходите отказ `rm -rf`.
6. Исходные сторонние registrations/plugins, которые установщик переместил или заменил, могут восстановиться: это откат изменений установки. Удалённые отдельно пользователем сторонние пакеты не переустанавливаются. Общие ключи сервисов и входы не удаляются; пересылки секретов нет. Checkout, из которого агент выполнял процедуру, и npm download cache принадлежат пользователю/npm: после проверки агент может удалить только созданный им отдельный checkout, не текущий проект и не весь npm cache. Старые версии до 0.1.12 могли оставить временные proxy-каталоги вне `.agent-context`; удаляйте их только при подтверждённой принадлежности, не по одному похожему имени.
7. Проверьте, что `.agent-context` отсутствует, глобальный `@alexkirs/agent-context` отсутствует, собственные launcher/provider/hooks/retrieval/plugin исчезли из затронутых файлов. Повторный запуск должен вернуть `already_removed`. Закройте и заново откройте агент: уже загруженный модуль не выгружается правкой файла. Сообщите точные оставшиеся исключения; не обещайте полный охват неизвестных конфигураций.

Удаление уничтожает локальную историю инцидентов и резервные копии пакета. Опубликованные GitHub issues и существующие Langfuse traces не удаляются; это отдельные внешние данные.

## Кандидат 0.4.0: выбор компрессора

Это кандидат для тестов, не опубликованный стабильный релиз. `provider show` различает настройки и работающие процессы. `provider test <headroom-local|supercompress|scaledown|all>` использует только синтетический context, без модельных запросов. `provider select <name>` сохраняет выбор и сообщает необходимость перезапуска; сам рабочий процесс не переключает. Ключи облачных провайдеров остаются в локальном защищённом профиле. План нового onboarding и обратимого удаления описан в [проекте врапера](docs/WRAPPER-DESIGN.md).

## Телеметрия кандидата 0.4.4

Native exporter остаётся источником реальных model input/cache/output и доступной ему стоимости. RTK-события содержат stable event ID, package/engine version, native session/call при наличии, exit code, latency и только явно помеченные `rtk_estimate`. CLI не выходит из sandbox: если loopback недоступен, монитор повторяет отправку сохранённых метаданных. `submitted` означает принятие локальным exporter, не подтверждённую доставку в Langfuse. MCP сохраняет оригинальные bytes; поиск фрагментов не означает доказанную экономию задачи.

Лимиты: справочные UTF-8 файлы ≤1 MiB, последние 100 оригиналов/7 дней; один MCP хранит ≤100 индексов. RTK recovery: ≤500 завершённых запусков, 7 дней, 512 MiB. `uninstall --dry-run` показывает временные recovery-папки; uninstall отказывается при живой native-команде и удаляет свои завершённые данные. Истёкший ref требует чтения исходного файла. Активные старые proxy-сессии не прерываются; миграция остаётся pending до их завершения.

Codex: cache-индекс использует штатное per-tool `approval_mode=approve` после выбранного подключения MCP; существующее явное решение пользователя сохраняется. Общие approval/sandbox settings не меняются. Read-only sandbox может запретить recovery storage: тогда CLI передаёт исходную команду без сжатия.

## Диагностика ошибки в текущей сессии

Короткий рецепт для агента: [SESSION-DIAGNOSTICS.md](docs/SESSION-DIAGNOSTICS.md). Native session ID, время и фактическая версия — основа поиска; отсутствие записи не означает отсутствие ошибки.
