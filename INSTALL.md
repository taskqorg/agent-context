# Онбординг и удаление через агента

## Подключение команды без сервисных ключей

Кандидат 0.2.1 добавляет GitHub Device Flow и общий gateway. Публичный адрес команды: `https://langfuse.ufobe.com/api/public/agent-context`. OAuth App зарегистрирован; на FRA проверены реальный вход, обновление токенов и доставка. Процедура владельца и статус квалификации: [TEAM-ONBOARDING.md](docs/TEAM-ONBOARDING.md). Рабочая миграция Mac и квалификация Windows ещё не завершены; не обещайте готовый массовый онбординг. Кандидат закреплён commit `bfc1cb24dda2c7b384e80914075d13b013782ca7`, не moving main.

Если команда предоставила адрес готового gateway, агент объясняет передачу выбранного tool context в SuperCompress и native conversation/tool telemetry в Langfuse. Затем запускает `agent-context connect <HTTPS gateway URL>` в локальном терминале и показывает пользователю только ссылку `https://github.com/login/device` и временный публичный код. Пользователь подтверждает доступ на GitHub. OAuth token, device token и сервисные ключи в чат не передаются. После успешного подключения агент выполняет `setup`, `doctor --fix --live`, `telemetry verify` и настоящий ход для каждого установленного агента; обычные login/model/approval и native hook trust сохраняются.

В этом режиме отдельные Langfuse/SuperCompress credentials у сотрудника не запрашиваются. Профиль хранит только отзываемый доступ устройства; native exporters отправляют OTLP в loopback proxy с закрытой ограниченной очередью. Native Windows и WSL получают разные устройства и порты. Если native exporter отсутствует или hook не доверен, это остаётся `needs_attention`, а не успешной настройкой. Явное отключение capture владельцем сохраняется. Обычный прямой режим ниже остаётся доступен для независимой установки.

Текущий кандидат усиленной телеметрии: [TELEMETRY-DELIVERY.md](docs/TELEMETRY-DELIVERY.md). `setup` теперь требует валидных credentials, native exporter и проверенной доставки для статуса `configured`; при их отсутствии сжатие сохраняется, onboarding сообщает `needs_attention`. Проверка доставки: `agent-context telemetry verify`, только небольшой синтетический OTLP span. Проверка реального native exporter выполняется отдельно.

При онбординге агент сначала объясняет, какие данные отправляются в SuperCompress/Langfuse, затем открывает локальный терминал для пользователя: `agent-context set-key` и `agent-context set-langfuse`. В интерактивном терминале ввод ключей скрыт; пользователь вводит их сам. Не просите ключи в чате, не передавайте их через аргументы команд и не читайте сохранённые ключи обратно в отчёт. Для автоматического private provisioning команды также поддерживают stdin: ключ SC текстом, Langfuse JSON `{public_key,secret_key,base_url}`. Файлы создаются с mode 0600; для Windows отдельно проверяется защита пользовательского профиля через ACL. Дальше агент выполняет `setup`, проверку доставки и настоящий ход. Отсутствующие Codex plugins ставятся штатным CLI; native hook trust не обходится. Этот independent native plugin сохраняется при удалении пакета; удаление самого exporter выполняется штатными средствами агента по отдельной просьбе.

Этот файл — процедура для Codex, Claude Code и Hermes, когда пользователь просит установить или удалить Agent Context. Канонический репозиторий: https://github.com/taskqorg/agent-context. Не выдавайте установку кандидата за квалифицированный стабильный релиз.

## Установка

1. Определите OS пользователя агента и его фактический профиль. Native Windows и WSL — разные установки; Windows-проект в WSL не превращает Windows-агента в Linux-агента. Дополнительные профили требуют отдельной проверки. Не переносите входы между хостами.
2. Проверьте Node 22+, npm, Git и установленный Python 3.11–3.13 с поддержкой `venv`/`ensurepip`. На Debian/Ubuntu/WSL может потребоваться отдельный пакет `python3.12-venv` (подставьте версию Python). Если зависимости отсутствуют, назовите недостающие и согласуйте установку системных зависимостей. Не заменяйте системный Python. Уже установленный подходящий интерпретатор можно выбрать через `AGENT_CONTEXT_PYTHON`. Объясните, что tool results проходят через локальный proxy и оплаченный SuperCompress; Langfuse необязателен. Публичные инциденты — только разрешённые метаданные; предложите `--no-report`, если пользователь не хочет отправку.
3. Прочитайте существующие настройки только установленных агентов и текущего проекта. Не выводите ключи, login-файлы или полный config. Найденное другое сжатие покажите пользователю. При разрешении удалить его сохраните закрытые копии и удалите только подтверждённые конфликтующие подключения. Не отключайте другие плагины по догадке. Не заменяйте неизвестный custom provider/proxy.
4. Используйте имеющийся `~/.supercompress/config.json` (`api_key`) или `SUPERCOMPRESS_API_KEY`. Если ключа нет, предложите приватный ввод; не просите прислать ключ в чат и не ставьте его в argv/log. `agent-context set-key` читает stdin. Не копируйте секреты с других машин. Langfuse подключается из существующего локального профиля; без него сжатие работает.
5. В подготовленной среде:

   ```sh
   npm exec --yes --ignore-scripts --package=github:taskqorg/agent-context -- agent-context setup
   ```

   Для рассмотренной версии закрепите полный Git SHA вместо moving main. Альтернатива для разработки/удаления прежнего пакета: отдельный checkout этого репозитория, `npm ci --ignore-scripts`, `node bin/agent-context.js setup`. Не клонируйте поверх существующего проекта. Пакет не устанавливает самих агентов и не открывает новую подписку.
6. Прочитайте `onboarding`, отсутствующие агенты, предупреждения и ошибки. `needs_attention` требует исправления перечисленных условий. Пропущенный агент не считается настроенным. Выполните `doctor --fix --live` через установленный CLI или приватный launcher (`node <home>/.agent-context/launcher.mjs doctor --fix --live`). Эта установка через npm exec не создаёт постоянную глобальную shell-команду.
7. Перезагрузите подключения штатным способом, не прерывая чужие активные сессии. Выполните один разрешённый синтетический tool-result тест у каждого проверяемого агента. Не меняйте approval policy, вход или модель ради теста. При отсутствии разрешённого инструмента назовите блокер; не обходите его.
8. Дайте короткий результат: установленные агенты и версия, сервисы, конфликты, наличие ключа без значения, телеметрия, автообновления, действительная runtime-проверка и оставшиеся блокеры. Health, размер текста и реальные model-input token savings — разные доказательства. Стабильные patch-обновления проверяются не чаще раза в час; новые minor/major требуют миграции.

## Полное удаление

Просьба пользователя удалить пакет разрешает этот шаг. Не удаляйте действующие профили на машинах только ради проверки процедуры.

1. Попросите завершить остальные сессии, использующие proxy; удаляйте из отдельного терминала/агента, который не использует удаляемый proxy. Занятый сервис возвращает отказ, без убийства процесса. На каждом OS-профиле процедура отдельная.
2. Если установленная версия ещё не поддерживает uninstall, подготовьте отдельный свежий checkout репозитория и зависимости; запускайте `node bin/agent-context.js uninstall`. Новая установка для этого не нужна. После появления команды в установленной версии можно использовать CLI или приватный launcher.
3. Сначала `uninstall --dry-run`: проверьте перечисленные пути восстановления, migrated plugins и каталог данных. Preview не изменяет файлы и не останавливает сервисы.
4. Выполните `uninstall`. Команда проверяет журналы и backup hashes, восстанавливает изменения всех завершённых установок, останавливает только свои сервисы после проверки owner/PID и control token, удаляет свои данные и global npm-пакет. Установка/обновление сериализованы с удалением. Не удаляйте `.agent-context` вручную до восстановления настроек.
5. Более поздние изменения других JSON/TOML/YAML настроек сохраняются. При таком слиянии TOML/YAML форматируется заново; full-line comments сохраняются, inline comments могут потеряться. Изменённые собственные значения, неизвестные/повреждённые журналы, symlinks или живой сервис с неподтверждённой идентичностью вызывают отказ. Сохраните локальную квитанцию и согласуйте точечное исправление — не обходите отказ `rm -rf`.
6. Исходные сторонние registrations/plugins, которые установщик переместил или заменил, могут восстановиться: это откат изменений установки. Удалённые отдельно пользователем сторонние пакеты не переустанавливаются. Общие ключи сервисов и входы не удаляются; пересылки секретов нет. Checkout, из которого агент выполнял процедуру, и npm download cache принадлежат пользователю/npm: после проверки агент может удалить только созданный им отдельный checkout, не текущий проект и не весь npm cache. Старые версии до 0.1.12 могли оставить временные proxy-каталоги вне `.agent-context`; удаляйте их только при подтверждённой принадлежности, не по одному похожему имени.
7. Проверьте, что `.agent-context` отсутствует, глобальный `@alexkirs/agent-context` отсутствует, собственные launcher/provider/hooks/retrieval/plugin исчезли из затронутых файлов. Повторный запуск должен вернуть `already_removed`. Закройте и заново откройте агент: уже загруженный модуль не выгружается правкой файла. Сообщите точные оставшиеся исключения; не обещайте полный охват неизвестных конфигураций.

Удаление уничтожает локальную историю инцидентов и резервные копии пакета. Опубликованные GitHub issues и существующие Langfuse traces не удаляются; это отдельные внешние данные.
